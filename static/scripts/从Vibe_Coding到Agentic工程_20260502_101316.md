# 从 Vibe Coding 到 Agent Engineering：Andrej Karpathy 眼中的 AI 编程新纪元

## 编程史上最“落后”的时刻

去年年底，Andrej Karpathy 说了一句让整个科技圈都震惊的话：**他从来没有感觉自己作为一个程序员，这么落后过。**

这话出自 Karpathy 之口，分量格外重。他可是 OpenAI 的联合创始人，当年在 Tesla 一手搞定了 Autopilot，更是“Vibe Coding”这个词的发明者。连他都觉得跟不上时代了，那到底发生了什么？

Karpathy 说，这种感觉其实是兴奋和不安的混合体。过去一年多，他一直在用各种 AI 编程工具，但直到去年十二月，事情发生了质变。以前 AI 写的代码块总得手动改改，但十二月开始，**最新的模型产出的代码几乎不需要修正**。他一次又一次地向 AI 提需求，AI 一次又一次地给出完美结果。到最后，他已经记不清上次自己动手改代码是什么时候了。

“我彻底陷入了 Vibe Coding 的状态。”他说。

很多人对 AI 的印象还停留在 ChatGPT 那个层面，但 Karpathy 强调，**从去年十二月开始，事情已经彻底变了**。尤其是那种“智能体协同工作流”（agentic coherent workflow），真正开始发挥作用了。他的个人项目文件夹现在塞得满满当当，全是靠 Vibe Coding 搞出来的东西。

## 软件 3.0：一个全新的计算范式

Karpathy 一直在强调一个概念：**大语言模型不是更好的软件，而是一个全新的计算范式。**

他回顾了软件发展的三个阶段：

**软件 1.0**：我们手写代码，精确告诉计算机每一步要做什么。

**软件 2.0**：我们通过创建数据集、训练神经网络来编程。编程变成了“安排数据集、设定目标、设计网络架构”。

**软件 3.0**：编程变成了**提示词工程**。你的上下文窗口（context window）就是你的操作杆，大语言模型就像是一个解释器，读取你的上下文，在数字信息空间中执行计算。

这个转变听起来抽象，但 Karpathy 给了两个非常生动的例子。

### 例子一：安装 OpenCL

以前你要装 OpenCL，会去找一个 shell 脚本。但问题是，为了适配各种不同的平台和计算机，这些脚本会变得极其复杂。你被困在软件 1.0 的思维里，非得写代码不可。

而现在，OpenCL 的安装方式变成了一段你要复制粘贴给你的 AI 智能体的文本。**这段文本不需要精确描述所有细节**，智能体有自己的智能，它会查看你的环境、你的电脑，然后智能地执行操作，甚至在过程中自我调试。

“这强大太多了，”Karpathy 说，“现在的编程范式变成了：你要给智能体复制粘贴什么文本？”

### 例子二：MenuGen

Karpathy 做了个叫 MenuGen 的应用。你去餐厅，菜单没图片，不知道那些菜长什么样。他就用 Vibe Coding 搞了个应用：拍下菜单照片，上传，应用就会 OCR 识别菜名，再用图像生成器给每道菜配图，最后重新渲染出一个带图片的菜单。

但后来他看到了软件 3.0 版本的 MenuGen：**直接把菜单照片扔给 Gemini，说一句“用 Nanobanana 把菜品的图片叠加到菜单上”，Nanobanana 就直接返回了一张图片，像素级地在原菜单照片上渲染出了每道菜的图片。**

Karpathy 当时就震惊了：“我意识到，我做的 MenuGen 应用完全是多余的。它还在用旧的范式工作。那个应用根本不应该存在。”

在软件 3.0 范式里，**神经网络承担了越来越多的工作**，你的提示词或上下文就是一张图片，输出也是一张图片，中间不需要任何应用层。

## 2026 年会发生什么？

如果按照这个趋势外推，2026 年的编程会是什么样？

Karpathy 说，这个外推看起来会很奇怪。你可以想象一个**完全由神经网络驱动的计算机**：你输入原始视频或音频，神经网络用扩散模型直接渲染出一个 UI，这个 UI 是独一无二的、为那个瞬间定制的。

他还提到，在计算机早期，人们其实不确定计算机到底是像计算器还是像神经网络。五六十年代的时候，这两条路都不明确。最终我们走了计算器的路，建立了经典计算。而神经网络目前还在现有计算机上虚拟化运行。

但 Karpathy 认为，**这种局面会翻转**：神经网络会成为宿主进程，CPU 反而变成协处理器。神经网络的算力消耗会成为主导，它们用工具调用就像用一个历史遗留的附件，但真正掌控全局的是神经网络。

## 可验证性：AI 能力的“锯齿形”分布

Karpathy 花了很多时间思考一个概念：**可验证性（verifiability）**。

为什么 AI 的能力分布这么“锯齿状”？有些领域它强得离谱，有些领域却弱智得可笑？

原因在于，前沿实验室训练大语言模型时，用的是大规模的强化学习环境。模型通过获得验证奖励来进步。所以，**模型在数学、编程这类可验证的领域能力特别强**，而在那些难以验证的领域就表现平平。

Karpathy 举了一个令人哭笑不得的例子：今天最先进的模型能同时重构一个 10 万行代码的代码库，或者发现零日漏洞，但当你问它“我想去 50 米外的洗车店洗车，应该开车还是走路？”它居然会回答“走路，因为太近了”。

“这太疯狂了，”Karpathy 说，“一个能重构 10 万行代码的模型，居然建议你走路去洗车？”

这种锯齿状能力分布告诉我们两件事：第一，模型确实还有问题；第二，**你需要在循环中保持参与**，把它们当工具用，时刻关注它们在做什么。

还有一个有趣的例子：从 GPT-3.5 到 GPT-4，国际象棋能力提升了很多。很多人以为这是能力的自然进步，但实际上，是因为 OpenAI 有人在预训练数据里加了大量国际象棋数据。**模型能力的峰值，很大程度上取决于实验室在数据分布里放了什么。**

所以，Karpathy 说，你拿到的模型没有说明书。它在某些领域如鱼得水，在另一些领域却挣扎不已。你需要自己去探索，搞清楚你的应用场景是在模型的“舒适区”里，还是在外围。如果在外围，你就得考虑微调，自己做些工作。

## 给创业者的建议

如果你是个创始人，想解决一个可验证的问题，但发现实验室已经在数学、编程这些最明显的领域取得了巨大进展，你该怎么办？

Karpathy 的建议是：**可验证性本身就是一个杠杆**。即使实验室没有直接关注你的领域，只要你的领域是可验证的，你就可以自己创建强化学习环境，做自己的微调。这技术是有效的，你只需要有大量多样的数据集和 RL 环境，然后拉一下杠杆，就能得到不错的结果。

至于哪些领域还有机会，Karpathy 卖了个关子：“我不想在台上剧透，但确实有一些非常有价值的强化学习环境，还没有被实验室充分探索。”

## 从 Vibe Coding 到 Agent Engineering

去年，Karpathy 发明了“Vibe Coding”这个词。而现在，他认为我们进入了一个更严肃的阶段：**Agent Engineering（智能体工程）**。

两者的区别是什么？

**Vibe Coding 是提升所有人的下限**。每个人都能用它搞出点东西来，这太棒了。

**Agent Engineering 是保持专业软件的质量水准**。你不能因为 Vibe Coding 就引入安全漏洞，你仍然要对你的软件负责。问题是：你能不能更快？剧透：你可以。但怎么正确地做到？

Karpathy 把 Agent Engineering 看作一门工程学科。智能体是这些“锯齿状”的实体，有点不稳定，有点随机，但极其强大。**如何协调它们，在保持质量的同时加速，这就是 Agent Engineering 的领域。**

他提到，过去人们说“10 倍工程师”，但在 Agent Engineering 时代，**这个倍数远不止 10**。那些擅长这个的人，效率提升远超 10 倍。

## 什么是真正的 AI 原生程序员？

如果让你观察两个人用 AI 编程工具，一个平庸，一个真正的 AI 原生，你怎么区分？

Karpathy 说，关键在于**是否充分利用了所有工具特性，是否投资于自己的设置**。就像以前工程师会钻研 Vim 或 VS Code 一样，现在你要钻研 Claude Code 或 Codex。

他还提到，很多公司还没调整招聘流程。如果你还在出算法题，那还是旧范式。**真正的 AI 原生招聘应该这样**：给候选人一个大项目，比如“用智能体写一个 Twitter 克隆”，然后让其他智能体去攻击这个网站，看它能不能扛住。

## 什么人类技能变得更值钱了？

随着智能体做越来越多的事，什么人类技能变得更重要了？

Karpathy 的回答很直接：**审美、判断力、品味，以及一点监督**。

他讲了一个 MenuGen 开发中的趣事：用户用 Google 账号登录，但用 Stripe 购买积分。这两个系统都有邮箱地址。他的智能体居然试图用 Stripe 的邮箱去匹配 Google 的邮箱，来关联资金。但如果用户用了不同的邮箱，资金就关联不上了。

“这种错误太奇怪了，”Karpathy 说，“为什么要用邮箱来关联资金？邮箱可以是任意的。”

所以，**人类需要负责规格和计划**。你需要和智能体一起设计详细的规格文档，你负责监督和顶层设计，智能体负责填充细节。

Karpathy 自己已经记不住 PyTorch 和 NumPy 的各种 API 细节了——“keepdims 还是 keep_dim？dim 还是 axis？reshape 还是 permute？我不记得了。因为不需要记得，这些细节由智能体处理。”

但你必须理解底层原理：比如张量有视图（view）和存储（storage）的概念，操作视图比复制存储更高效。**你仍然需要理解这些基础，但 API 的细节可以交给智能体。**

## 我们是在召唤“幽灵”，不是在建造“动物”

Karpathy 写了一篇很有深度的文章，讨论“动物 vs 幽灵”的比喻。他认为，**我们不是在建造动物，而是在召唤幽灵**。

动物有内在动机、好奇心、求知欲，这是进化赋予的。而大语言模型是由数据和奖励函数塑造的“锯齿状智能体”，没有这些内在驱动力。

这个区分为什么重要？因为**如果你对它们是什么有正确的理解，你就能更有效地使用它们**。

比如，你对它们吼叫不会让它们工作得更好或更差，它们没有情绪。它们就是统计模拟电路，预训练给了它们统计能力，强化学习在之上增加了某些能力。

Karpathy 说，这更多是一种心态：**对模型保持怀疑，不断测试它在哪些领域可靠，哪些领域不可靠**。

## 智能体原生世界长什么样？

当智能体不仅会聊天，还有真实权限、能采取行动时，世界会变成什么样？

Karpathy 说，**一切都要重写**。目前所有东西都是为人类设计的。他最受不了的就是文档：“为什么还在告诉我该做什么？我不想做任何事。告诉我该复制粘贴什么给我的智能体！”

他希望看到更多“智能体优先”的基础设施：把工作负载分解成传感器和执行器，用智能体能理解的方式描述任务。

MenuGen 的开发经历让他感触很深：最麻烦的不是写代码，而是部署到 Vercel——要配置各种服务、设置 DNS、点各种菜单。“我希望我能给 LLM 一个提示词‘构建 MenuGen’，然后什么都不用碰，它就直接部署到网上了。”

最终，Karpathy 认为我们会走向一个世界：**每个人都有智能体代表，组织也有智能体代表。我的智能体和你的智能体对话，来安排会议细节。**

## 什么还值得深入学习？

最后一个问题关于教育：当智能变得廉价时，什么还值得深入学习？

Karpathy 引用了一条让他反复思考的推文：**“你可以外包你的思考，但你无法外包你的理解。”**

信息最终还是要进入你的大脑。你仍然是系统的一部分。你需要知道我们在建什么、为什么值得做、怎么指挥你的智能体。**理解仍然是瓶颈。**

这也是为什么 Karpathy 对“LLM 知识库”项目如此兴奋。他用这些工具来增强自己的理解：读一篇文章，让 AI 帮他构建一个 wiki，然后他不断地提问、探索。

“这些工具最终是增强理解的工具，”他说，“而理解仍然是稀缺的。如果你不理解，你就无法做一个好的导演。”

最后他笑着说：“我很期待几年后回到这里，看看我们是否已经被完全自动化，连理解都由 AI 代劳了。”
